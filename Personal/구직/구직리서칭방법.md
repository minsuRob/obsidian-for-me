# 구직 리서칭 방법

> 작성일: 2026-10-14
> 대상: 그룹바이(groupby.kr) 채용공고 상세 조사 — [[그룹바이]], [[그룹바이-비개발]]
> 목적: 공고 목록을 모은 뒤, 각 공고의 상세 정보를 사람이 읽기 좋은 Markdown으로 쌓아 가는 방법을 기록한다.

## 1. 전체 흐름

1. **목록 수집:** 필터 걸린 그룹바이 목록 페이지에서 공고 링크를 모두 모은다.
   - 2026-10-14 기준 화면 표시 520개, 실제 수집 링크 519개
2. **1차 분류:** 목록 정보(공고명·스택)로 개발 / 비개발·개발 인접을 나눈다.
   - 개발: 소프트웨어·데이터·AI/ML·로봇 소프트웨어·임베디드·DevOps·보안 솔루션 개발
   - 비개발: QA, 보안 컨설팅, 하드웨어, 기계·전장, 설계, 품질, 비소프트웨어 연구, PM·디자이너·마케터
3. **상세 조사:** 인앱 브라우저로 공고를 하나씩 열어 본문을 읽고, 정해진 항목으로 요약한다.
4. **누적 저장:** 공고 하나를 처리할 때마다 결과를 저장하고, 주기적으로 두 Markdown 파일에 반영한다.
5. **재분류:** 상세 본문을 보고 분류가 명백히 다르면 파일을 옮긴다. 옮긴 내역은 파일 머리말에 기록한다.

## 2. 공고별 조사 항목

```markdown
### 번호. 공고명 — 회사명

- 위치:
- 가까운 역·도보:
- 주요 업무:
- 기술 스택:
- 회사 특징:
- 회사 방향성:
- 공고 마감일:
- 원문:
- 목록 노출 정보:   (기존 목록 정보는 지우지 않고 유지)
```

작성 원칙:

- 공고에 없는 정보는 추측하지 않고 `공고에 미기재`로 쓴다.
- 마감일이 없으면 `마감일 미기재`로 쓴다.
- 역·도보 시간은 공고에 적힌 값을 먼저 쓰고 `(공고 명시)`를 붙인다.
- 공고에 없으면 근무지 주소를 근거로 보완하고 반드시 `(추정)`을 붙인다.
- 상세 주소가 없으면 `공고에 미기재 (상세 주소 없음)`으로 쓴다.
- 회사 특징·방향성은 공고 본문과 회사 소개에서 확인한 내용만 요약한다.
- 아직 조사하지 못한 공고는 `상세 조사: 미조사`로 표시하고, 링크와 목록 정보는 그대로 둔다.

## 3. 브라우저 사용 방법

- Claude 데스크톱 앱의 **인앱 브라우저**를 쓴다.
- **그룹바이에 로그인한 상태여야 한다.** 로그인은 사용자가 직접 한다.
  - 로그인하지 않으면 약 30건 이후 가짜 데이터만 나온다.
- 메모리를 고려해 탭은 최대 2개까지만 쓴다. 현재는 차단 때문에 1개만 쓴다.
- 공고 페이지 구조:
  - 회사명 / 온도 / 지역 / 인원·투자단계 / 분야 / 한줄소개 / 복지
  - 공고명 → 포지션·경력·특이사항·스킬
  - 주요업무 → 자격요건 → 우대사항 → 채용절차 → 근무지
  - 근무지 주소는 지도 아래 `© NAVER Corp.` 다음 줄에 있다.
- 공고를 연 뒤 렌더링이 끝날 때까지 기다렸다가 `<main>` 본문을 읽는다. `관련 채용 공고` 앞부분까지만 쓴다.

## 4. 그룹바이 열람 제한 — 가장 중요한 주의점

그룹바이는 짧은 시간에 공고를 많이 열면 **가짜 데이터**를 보여준다.

- **증상**
  - 회사명과 공고명 앞에 `[표시 제한]`이 붙는다.
  - 회사명과 직무가 실제와 다르다 (예: 개발 공고인데 "마케터", "QA 엔지니어"로 표시).
  - 본문(주요업무·자격요건)이 없고 근무지는 시·구만 나온다.
- **헷갈리기 쉬운 점**
  - 공고를 연 직후에는 정상 공고도 탭 제목에 `[표시 제한]`이 잠깐 보인다.
  - 몇 초 뒤 실제 공고로 바뀌므로, 렌더링이 끝난 뒤의 본문으로만 판단한다.
- **판단 기준**
  - 렌더링이 끝난 뒤 본문 앞부분이나 탭 제목에 `[표시 제한]`이 남아 있으면 차단된 것이다.
  - `주요업무`·`자격요건`·`근무지` 중 어느 것도 없어도 차단된 것으로 본다.
- **가짜 데이터는 절대 저장하지 않는다.**
  - 저장 후에는 결과의 공고명을 원래 목록의 공고명과 대조해 섞여 들어간 것이 없는지 확인한다.
- **해보고 안 된 방법**

  | 방법 | 결과 |
  |---|---|
  | 페이지 HTML을 빠르게 대량으로 가져오기 | 약 30건 이후 전부 가짜 데이터 |
  | 숨긴 iframe으로 렌더링해 읽기 | 처음부터 가짜 데이터 |
  | 로그인 후 25초·60초 간격 | 2~3개 뒤 다시 차단 |

- **우회는 하지 않는다.** 사이트의 제한을 존중하고, 간격을 늘려 사람이 보는 속도로만 연다.

## 5. 적응형 간격 (현재 방식)

공고 사이 대기 시간 D를 두고, 막히면 늘려 가며 **문제없는 간격**을 찾는다.

1. D는 120초(2분)에서 시작한다.
2. 공고 하나를 저장하면 D초 쉬고 다음 공고를 연다.
3. 막히면 저장하지 않는다. D를 30초 늘리고(최대 360초) 그만큼 쉰 뒤 같은 공고를 다시 연다.
4. 같은 공고가 3번 연속 막히면 재시도 목록에 넣고 다음 공고로 넘어간다.
5. D가 360초인데도 3번 연속 막히면 멈추고 한참 기다린 뒤 재개한다.
6. D는 줄이지 않는다.
7. 공고를 열 때마다 시각·간격·결과를 기록한다.

관찰 기록 (2026-10-14):

| 시각 | 공고 | 간격 | 결과 |
|---|---|---|---|
| 18:07 | 9358 | 2분 | 정상 |
| 18:10 | 354 | 2분 | 정상 |
| 18:13 | 355 | 2분 | 막힘 → 2분 30초 |
| 18:17 | 355 | 2분 30초 | 막힘 → 3분 |
| 18:21 | 355 | 3분 | 정상 |

- 연속으로 막힌 뒤에는 30분 이상 기다려야 풀린 적이 있다.
- 2분만 쉬어도 1개는 열리는 경우가 있었다.
- 3분 간격으로 처리하면 공고 500개에 약 24시간이 걸린다.

## 6. 저장과 재개

- 공고 하나를 처리할 때마다 결과를 공고 ID별 JSON으로 즉시 저장한다. 중간에 멈춰도 처리한 내용은 남는다.
- 다시 시작할 때는 이미 저장된 ID를 건너뛰고 비어 있는 공고부터 이어서 처리한다.
- 반영 스크립트가 JSON을 모아 [[그룹바이]]와 [[그룹바이-비개발]]을 다시 만든다.
  - 기존 목록 정보와 링크는 유지한다.
  - 머리말에 상세 조사 완료 수, 미조사 수, 분류 이동 내역을 갱신한다.
- 반영할 때마다 각 파일의 공고 수와 링크 수를 확인한다 (현재 개발 480 + 비개발 39 = 519).
- 작업 저장소 사본과 iCloud Obsidian 볼트 사본에 같은 내용을 반영한다.

## 7. 역할 분담 (Claude 작업 시)

- 메인 대화는 진행 관리, 결과 검증, 파일 반영을 맡는다.
- 공고 열람과 요약은 작업자(서브에이전트)에게 맡긴다. 작업자는 탭 하나만 쓰고, 지시서의 간격 규칙을 지킨다.
- 작업자는 한 번 실행에 약 20개까지만 처리하고 보고한다. 이렇게 해야 작업 맥락이 너무 커지지 않는다.
- 작업자 보고 뒤에는 공고명 대조로 검증하고 파일에 반영한 다음, 다음 배치를 시작한다.

## 8. 남은 과제

- 3분 간격이 계속 유지되는지 확인한다.
- 계속 제한되는 공고(예: 7250)는 마지막에 다시 시도한다.
- 사이트 표시 520개와 실제 수집 519개의 차이 원인은 아직 확인하지 못했다.
